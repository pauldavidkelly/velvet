# Glove80 keymap formats: Layout Editor JSON vs ZMK `.keymap`

Research for [#3](https://github.com/pauldavidkelly/velvet/issues/3), part of the map [#1](https://github.com/pauldavidkelly/velvet/issues/1). Researched 2026-10-10.

**Question.** Which input format(s) should Velvet ingest: Layout Editor JSON, a ZMK `.keymap` file, or reading the keymap off the keyboard over ZMK Studio RPC? How do layers, layer-taps, momentary and toggle layers, hold-taps (home-row mods), combos and macros appear in each format? How does each binding map to one of the 80 physical key positions and their geometry? Which parsers already exist?

**Status of the user's own keymap.** No `keymaps/` directory exists in the repo yet, so these findings come from MoErgo's sources and from published Layout Editor exports. Re-check them against the real export once it's added.

---

## TL;DR / recommendation

1. **Ingest the Layout Editor JSON export first.** It's plain JSON. Each layer is an array of exactly 80 binding objects in physical key-position order. Hold-taps, combos and macros that were built in the editor's GUI arrive as structured JSON (`holdTaps`, `combos`, `macros`). The browser needs no C preprocessor and no devicetree parser. MoErgo calls the Layout Editor "the recommended and simpler option" for most users [1].
2. **Bundle the physical geometry with the app.** Neither format carries it. MoErgo publishes it as a QMK-style `info.json` (label, row, col, x, y, rotation) [2], and the ZMK board definition carries the same data as a `physical_layout` [3]. Ship a static 80-key table derived from these sources.
3. **Treat the ZMK `.keymap` devicetree as a later, optional input.** It suits glove80-zmk-config users and other keyboards. Parsing it properly means running the C preprocessor (`#define`, `#include`, macros) and then parsing devicetree. That's what keymap-drawer does [12]. It's too heavy for the MVP.
4. **Know the limit of the JSON route.** Power users can bypass the GUI with `"Custom"` bindings: raw devicetree text that calls behaviours defined in the `custom_defined_behaviors` string. These keymaps are effectively ZMK source again (example: sunaku's Glorious Engrammer [9]). The MVP should detect `Custom` bindings and flag them as unsupported rather than guess. Whether the user's own keymap needs them is an open question (see the last section).
5. **ZMK Studio RPC (reading the keymap off the keyboard) is not an MVP route.** It returns layers, raw bindings and geometry, but no hold-tap internals, no combos and no macro contents. It needs a Studio-enabled firmware and an unlock key, and only works in Chromium. MoErgo's build pipeline could only build Studio from v26.09 (2026-10-01). **I couldn't confirm that Layout Editor builds enable it**, and the defaults don't (section 7).
6. **Expect the JSON to change.** MoErgo labels the JSON export *experimental*: "the JSON format may change" and import of old exports isn't guaranteed [4]. Validate exports at runtime, for example with a zod schema, and fail loudly on unknown shapes.

## 1. The two formats, and how to get each one

| | Layout Editor JSON | ZMK `.keymap` (devicetree) |
|---|---|---|
| How you get it | my.glove80.com: Settings, then enable **Local Backup and Restore**. **Export** then offers JSON [4]. | The Export button next to Save and Build in the Layout Editor gives `<layout_name>.keymap` [4]. Or it's the `config/glove80.keymap` file in a glove80-zmk-config repo [2]. |
| Nature | Structured data, editor-specific, "experimental" [4] | Source code: C preprocessor plus devicetree [5] |
| Positional bindings | `layers[i]` is an 80-element array | `bindings = < ... >` lists 80 whitespace-separated binding expressions per layer [2] |
| Layer references | Integer layer index in GUI bindings (`{"value": 3}`), or `LAYER_<Name>` inside Custom strings | Integers, or `#define` names |
| Hold-taps, combos, macros | JSON arrays (`holdTaps`, `combos`, `macros`), plus anything in `custom_defined_behaviors` (raw devicetree) | Devicetree nodes under `behaviors`, `macros` and `combos` [5][6][7] |
| Browser parsing cost | `JSON.parse` plus validation | Preprocessor plus devicetree parser |

The Layout Editor compiles the JSON into a `.keymap`. sunaku's repo commits a sample of that output, headed `/* THIS FILE WAS GENERATED BY GLOVE80 LAYOUT EDITOR */` [10]. That file shows exactly how the JSON concepts map onto ZMK, and it's used as evidence below.

Note: `config/keymap.json` in moergo-sc/glove80-zmk-config [2] is a **third shape**. It's a QMK-configurator-style file (`keyboard`, `keymap`, `layout`, `layer_names`, `layers`), and the same repo has a matching `info.json`. It is *not* the Layout Editor export, though its binding objects look the same (`{"value": "&kp", "params": [{"value": "F1", "params": []}]}`).

## 2. Layout Editor JSON schema (observed)

MoErgo publishes no schema. The shape below comes from 44 real Glove80 exports: sunaku's 10 layouts [9], basnijholt's TailorKey releases [11], and the examples in zmk-glovebox [13]. Every sampled layer array had exactly 80 entries.

### Top level

```jsonc
{
  "keyboard": "glove80",            // also "go60" for MoErgo's Go60 (KB_TYPE_GO_60 exists in generated output [10])
  "firmware_api_version": "1",
  "locale": "en-US",
  "uuid": "...", "parent_uuid": "...", "date": 1761753601,
  "creator": "...", "title": "...", "notes": "...", "tags": [],
  "unlisted": false, "layout_parameters": {},           // newer exports only
  "config_parameters": [{"paramName": "HID_POINTING", "value": "y"}],  // Kconfig overrides
  "layer_names": ["Base", "Lower", "Magic"],             // index i names layers[i]
  "layers": [[ /* 80 bindings */ ], ...],
  "holdTaps": [...], "combos": [...], "macros": [...], "inputListeners": [...],
  "custom_defined_behaviors": "",   // raw devicetree/C text, pasted into the generated .keymap
  "custom_devicetree": ""           // raw devicetree text
}
```

Sources: [9] `default.json` and `keymap.json`; [11] TailorKey releases.

### Binding objects (recursive)

```jsonc
{"value": "&kp", "params": [{"value": "A", "params": []}]}                 // key press
{"value": "&kp", "params": [{"value": "LS", "params": [{"value": "END", "params": []}]}]}  // modifier function LS(END)
{"value": "&mo", "params": [{"value": 16, "params": []}]}                  // momentary layer 16 (integer index)
{"value": "&thumb_v2_TKZ", "params": [{"value": 3, "params": []}, {"value": "BSPC", "params": []}]} // user hold-tap: hold layer 3, tap BSPC
{"value": "&HRM_left_pinky_v1B_TKZ", "params": [{"value": "LGUI", "params": []}, {"value": "A", "params": []}]} // home-row mod
{"value": "&trans", "params": []}, {"value": "&none", "params": []}
{"value": "Custom", "params": [{"value": "&thumb LAYER_Function ESC"}], "decoration": {"label": "Esc", ...}} // raw devicetree
```

* `value` is the behaviour reference (`&name`). Params nest because modifier functions such as `LS(...)` and `LC(...)` wrap keycodes. `value` can be a string or a number.
* Some newer exports leave out an empty `params` and add an optional `decoration` (label, icon, colour, description) [9]. Make both optional in the schema.
* Built-in references seen: `&kp &mo &to &tog &sk &trans &none &bt &out &rgb_ug &mkp &mmv &msc &caps_word &bootloader &reset`. MoErgo also provides `&magic` and `&lower` [9][11].
* Any other `&name` refers to an entry in `holdTaps` or `macros`, or to something defined in `custom_defined_behaviors`.

### `holdTaps[]`

```jsonc
{
  "name": "&HRM_left_index_middy_v1B_TKZ",   // includes the leading &
  "description": "...",
  "bindings": ["&kp", "&HRM_left_index_tap_v1B_TKZ"],  // [hold behaviour, tap behaviour]
  "tappingTermMs": 190, "flavor": "tap-preferred", "quickTapMs": 300,
  "requirePriorIdleMs": 100, "holdTriggerOnRelease": true,
  "holdTriggerKeyPositions": [57, 56, 55, 72, ...],   // 0-79 key positions
  "retroTap": false, "tapBehavior": "...", "holdBehavior": "..."  // rarer fields
}
```

Each binding's params go to the hold behaviour and the tap behaviour in that order. A use such as `&HRM_left_pinky (LGUI, A)` therefore means *hold for LGUI, tap for A*. ZMK defines the same rule: "first one to the hold behavior and second one to the tap" [6]. If `bindings[0]` is `&mo`, it's a **layer-tap** (the first param is a layer index). If it's `&kp`, it's a **mod-tap / home-row mod**. Field frequency across 572 sampled hold-taps: `name`, `bindings` and `tappingTermMs` always present; `flavor` 550; `holdTriggerKeyPositions` 484 [9][11][13].

### `combos[]`

```jsonc
{
  "name": "capslock_v1_TKZ", "description": "...",
  "binding": {"value": "&kp", "params": [{"value": "CAPS", "params": []}]},
  "keyPositions": [52, 57],     // 0-79 physical positions (here, both T1 thumb keys)
  "layers": [0, 2],             // layer indices; [-1] means all layers
  "timeoutMs": 50
}
```

zmk-glovebox's generator emits `layers` only when the value isn't `[-1]`, which confirms that `[-1]` means global [13 `zmk_generator.py:438`]. ZMK itself says that omitting `layers` "defaults to global scope" [7].

### `macros[]`

```jsonc
{
  "name": "&AS_Shifted_v1_TKZ", "description": "...",
  "bindings": [ {"value": "&macro_press", "params": []}, {"value": "&kp", "params": [{"value": "LSHFT"}]},
                {"value": "&macro_tap"}, {"value": "&macro_param_1to1"}, {"value": "&kp", "params": [{"value": "N1"}]},
                {"value": "&macro_release"}, {"value": "&kp", "params": [{"value": "LSHFT"}]} ],
  "params": ["code"],     // 0-2 params, i.e. ZMK macro / macro-one-param / macro-two-param
  "waitMs": 1, "tapMs": 1
}
```

The bindings use ZMK's macro control behaviours (`&macro_tap`, `&macro_press`, `&macro_release`, `&macro_pause_for_release`, `&macro_param_1to1`) [8]. A macro that types a string shows up as a run of `&kp` taps.

### Layer names, built-ins and generated defines

The editor generates `#define LAYER_<name> <index>` for every entry in `layer_names` [10, lines 63-95]. `Custom` strings refer to layers that way, for example `&thumb LAYER_Function ESC`. The editor also always injects some system behaviours [10, lines 660-795]:

* `&lower` = `ZMK_TD_LAYER(lower, LAYER_Lower)`: a tap-dance (tap or hold for momentary Lower, double-tap to toggle). It falls back to layer 0 if no layer is named "Lower".
* `&magic` = a hold-tap with `bindings = <&mo>, <&rgb_ug_status_macro>`. It's used as `&magic LAYER_Magic 0`: hold for the Magic layer, tap to show RGB status.
* `&bt_0`..`&bt_3`: Bluetooth profile select. System keys are out of scope for #1.

## 3. ZMK `.keymap` encoding (for reference and a later format)

Primary source: the ZMK docs [5][6][7][8], plus the canonical Glove80 keymap [2].

* **Layers** are child nodes of the `compatible = "zmk,keymap"` node. Each one has a `bindings` list with "one for each key position". Layer index is definition order: "the first layer is `0`". The highest active layer wins, and the base layer is always on [5].
* **Layer behaviours** [14]: `&mo N` is momentary, `&to N` enables N and disables every other layer except the default, `&tog N` toggles, and `&lt N KEY` is a layer-tap (a built-in hold-tap). The Glove80 default keymap also uses a tap-dance (`layer_td`: `<&mo LOWER>, <&to LOWER>`) [2].
* **Hold-taps** use `compatible = "zmk,behavior-hold-tap"`, `#binding-cells = <2>`, `bindings = <&hold>, <&tap>`, `flavor` (`hold-preferred | balanced | tap-preferred | tap-unless-interrupted`), `tapping-term-ms` (default 200) and `hold-trigger-key-positions` (sequential key positions from 0). `&mt MOD KEY` is the built-in mod-tap [6].
* **Combos** live in a separate `compatible = "zmk,combos"` node. Each child has `key-positions = <...>` (numbered "like the keys in your keymap, starting at 0"), `bindings`, optional `layers` and `timeout-ms`. They "are processed before the normal keymap" [7].
* **Macros** use `zmk,behavior-macro`, `-one-param` or `-two-param`, with `bindings`, `wait-ms` and `tap-ms` [8].
* **Keycodes** are C `#define`s in `dt-bindings/zmk/keys.h` with many aliases, for example `N1` = `NUMBER_1`, `LSHFT` = `LEFT_SHIFT`. Shifted symbols are pre-wrapped: `EXCL` = `LS(N1)` [3 `keys.h:103-109`]. Modifier functions `LS() LC() LA() LG()` and their right-hand forms are in `modifiers.h` [3]. **Velvet needs a ZMK keycode → character table, whatever the input format.** The JSON carries the same keycode names.

## 4. Physical key positions and geometry

**Position index (0-79).** The order is the same in both formats. It's row-major, left to right, row lengths **10 / 12 / 12 / 12 / 18 / 16**, as the canonical keymap's layout comment shows [2]. The Layout Editor gives each position a name (`POS_LH_C6R1 0` … `POS_RH_C6R6 79`) [10, lines 798-880]. MoErgo's `info.json` uses the same labels without `H` (`L_C6R1`) [2].

| Positions | Row | Contents (L = left hand, R = right hand) |
|---|---|---|
| 0-9 | R1 (function row) | L C6-C2, R C2-C6 (no C1 key on R1) |
| 10-21 | R2 (numbers) | L C6-C1, R C1-C6 |
| 22-33 | R3 | L C6-C1, R C1-C6 |
| 34-45 | R4 (home) | L C6-C1, R C1-C6 |
| 46-63 | R5 + upper thumbs | L C6-C1 (46-51), **L T1-T3 (52-54)**, **R T3-T1 (55-57)**, R C1-C6 (58-63) |
| 64-79 | R6 + lower thumbs | L C6-C2 (64-68), **L T4-T6 (69-71)**, **R T6-T4 (72-74)**, R C2-C6 (75-79) |

T1 is the thumb key nearest the letter columns, and the numbers run toward the middle of the board. The right hand is mirrored, so its index order is T3, T2, T1.

**Geometry.** `info.json` gives `x`, `y` in key units, with rotation `r` and origin `rx` for the thumb keys, for example `L_T1 x 6.4 y 4 r 20 rx 4` and `R_T1 x 10.7 y 4 r -20 rx 14` [2]. The ZMK board's `glove80-layouts.dtsi` has the same layout as `&key_physical_attrs w h x y rot rx ry` in centi-units (thumbs at ±20° to ±60°) [3]. The board's `matrix_transform` maps the electrical matrix (6 rows × 14 columns over two halves) onto those 80 positions [3 `glove80.dtsi`]. Velvet never needs the matrix, only the 80-position order.

**Fingers (inference, needs confirmation).** sunaku's finger-named home-row mods sit at 35 = LeftPinky (L_C5R4), 36 = Ringy (C4), 37 = Middy (C3) and 38 = Index (C2), mirrored on the right at 41-44 [9]. That gives C6 and C5 to the pinky, C4 to the ring finger, C3 to the middle finger and C2 and C1 to the index finger, with thumbs on T1-T6. Neither format records fingers, so Velvet should ship a default column → finger table that the user can override.

## 5. What Velvet has to derive (ingest model sketch)

ZMK resolves the keymap before the host ever sees a character (#1 Notes). So, for each character the user might type, Velvet has to find the **path** that produces it: which layer, which key positions, and which modifiers. From the JSON:

1. **Keycode → character**: `&kp X`, including `LS(X)`-style nesting and shifted aliases. Assume a host keyboard layout (US ANSI?). See the open questions.
2. **Layer access**: for each layer *L*, find the keys that activate it. Scan the lower layers for `&mo L`, `&to L`, `&tog L` and `&lt L _`, hold-taps whose `bindings[0]` is `&mo` with first param *L*, `&lower` (if *L* is named "Lower"), `&magic`, and combos whose binding does any of these. This drives the on-screen thumb-key highlight.
3. **Home-row mods / mod-taps**: hold-taps whose `bindings` are `["&kp", "&kp"]` (or whose tap side is a macro chain that ends in `&kp`). The tap output is the second param, and the hold modifier is the first. Note which modifiers, Shift especially, can be held on the opposite hand.
4. **Transparent bindings**: `&trans` falls through to the next lower active layer. Resolve the effective binding for each position on each layer.
5. **Combos**: a `keyPositions` set, active `layers`, and an output binding.
6. **Macros** can emit several characters, or modifier-wrapped output, from one key.
7. **Unsupported**: `Custom`, behaviours defined only in `custom_defined_behaviors`, mod-morph, and tap-dance beyond `&lower`. Detect these and report them.

## 6. Existing parsers and libraries

| Project | Language | What it does | Fit for Velvet |
|---|---|---|---|
| keymap-drawer (caksoylar) [12] | Python | Parses ZMK `.keymap` with pcpp (C preprocessor) plus its own devicetree parser. Handles hold-taps, combos and layers. Ships a Glove80 physical layout (`resources/extra_layouts/glove80.json`). | Reference only (Python). Its ZMK parser is the best model for a later `.keymap` importer. |
| zmk-glovebox (CaddyGlow) [13] | Python | Pydantic models for the Layout Editor JSON (`HoldTapBehavior`, `ComboBehavior`, `MacroBehavior`…), and JSON → `.keymap` generation. | Good cross-check for the JSON schema. Port the field list to zod. |
| zmk-layout-rs (CaddyGlow) | Rust | Rust port, with JSON samples (`examples/moergo_factory.json`). | Reference / test fixtures. |
| omarchy-moergo-companion (dphov) [15] | Rust | Parses Layout Editor JSON (`json_layout.rs`) and `.keymap` (`parser.rs`, tokenizer) to show Glove80 layers. | Reference for the same problem (showing layers). |
| nickcoutsos/keymap-editor | JS/React | Web GUI editor for ZMK keymaps (parses devicetree). | Possible devicetree-parsing reference. |
| `tree-sitter-devicetree` (npm, 0.15.0) | WASM/JS | Devicetree grammar with Zephyr extensions. | A building block if a browser `.keymap` importer is ever needed (it still needs a preprocessor). |

No TypeScript library parses the Layout Editor JSON. It's simple enough to write directly against a zod schema, so the MVP doesn't need a dependency.

## 7. Third route: read the keymap off the keyboard with ZMK Studio RPC

ZMK Studio lets a host read and edit the live keymap over an RPC protocol (protobuf), carried over USB serial or BLE GATT [16][17]. There's an official TypeScript client with Web Serial and Web Bluetooth transports (`@zmkfirmware/zmk-studio-ts-client`, `src/transport/serial.ts` and `gatt.ts`) [18]. In principle a browser app could read the keymap straight from the Glove80, with no export step.

**What the RPC exposes** (`zmk-studio-messages` protos [17]):

* `keymap.get_keymap` returns `Keymap { layers[] { id, name, bindings[] { behavior_id, param1, param2 } } }`. Bindings are in key-position order, as above.
* `keymap.get_physical_layouts` returns the physical layout with each key's `width, height, x, y, r, rx, ry`, so it would also supply the geometry.
* `behaviors.list_all_behaviors` and `get_behavior_details(id)` return a `display_name` and parameter metadata (`nil`, `constant`, `range`, `hid_usage` or `layer_id`).

**What it doesn't expose:**

* What a hold-tap actually does: its hold and tap sub-behaviours, flavour and tapping term. A home-row mod arrives as "behaviour #N with params (LGUI-usage, A-usage)". Velvet would have to guess from `display_name` that the tap side sends the second param.
* Combos, macro contents, and mod-morph or tap-dance internals. ZMK lists configuring combos and macros in Studio as "planned" [16]. So the RPC can't deliver the combos #1 wants to teach.
* Keycode names. Params are raw 32-bit HID usages with modifier bits, so Velvet would need its own decoder.

**Access hurdles:**

* `get_keymap`, `get_physical_layouts` and `get_behavior_details` are all `SECURED` handlers [3 `app/src/studio/*_subsystem.c`]. With Studio locking on (it's implied by default for RPC builds), the user must press a `&studio_unlock` key that's in their keymap before anything can be read [16].
* Only the central (left) half runs RPC on a split keyboard [3 `app/src/studio/Kconfig`: `select ZMK_STUDIO_RPC if !ZMK_SPLIT || ZMK_SPLIT_ROLE_CENTRAL`].
* USB needs the `studio-rpc-usb-uart` snippet. BLE transport defaults on whenever `ZMK_BLE` is set [3]. ZMK says BLE in the web app works on Linux only [16].
* Web Serial and Web Bluetooth are Chromium-only browser APIs.

**Is Studio on in MoErgo builds?** Not by default, as far as I could confirm. **I couldn't confirm what Layout Editor builds do.**

* The Glove80 board metadata lists `studio` as a feature (`glove80.zmk.yml`), and its physical layout is defined in a Studio-compatible way [3]. But neither the Glove80 defconfigs nor the stock `glove80.conf` set `CONFIG_ZMK_STUDIO` [2][3].
* Until **v26.09 (released 2026-10-01)**, MoErgo's own nix build pipeline couldn't even build `CONFIG_ZMK_STUDIO=y`. PR #44 added the missing nanopb and zmk-studio-messages modules, and was tested on a Go60 over BLE [19]. glove80-zmk-config builds through that same nix pipeline (`config/default.nix`) [2].
* MoErgo's Layout Editor docs don't mention ZMK Studio anywhere I could find [4]. Two things remain unknown: whether the Layout Editor's build server has moved to v26.09, and whether its `config_parameters` (Kconfig overrides) would accept `ZMK_STUDIO=y`. Treat Studio as **not available on a typical Layout Editor-built Glove80** until that's tested on hardware.

**Verdict.** Studio RPC is a possible future convenience: plug in, unlock, and Velvet reads the layers and geometry. It isn't a replacement for the JSON. It loses hold-tap semantics and combos, needs firmware the user probably doesn't have, needs an unlock key and only works in Chromium. Keep it off the MVP critical path. If it's ever added, it could *refresh* bindings for a keymap whose structure came from JSON.

## Open questions surfaced (candidate tickets)

1. **Does the user's keymap use `Custom` bindings or `custom_defined_behaviors`?** If it does, the JSON-only MVP can't read those keys. Answering needs the export committed under `keymaps/`.
2. **Host keyboard layout**: which OS layout turns keycodes into characters (US ANSI assumed)? Is non-US out of scope for the MVP?
3. **Several paths to one character**: a capital can come from HRM Shift, sticky shift, caps-word or a Shift key, and a symbol can sit on a layer *and* on a combo. Which path does the tutor teach and expect, or does it accept any of them? This is a grilling topic that feeds Unlocking and the on-screen highlight.
4. **Finger assignment**: confirm the default column → finger table and decide whether the user can override it per key. It feeds the "each binding records finger and key" note in #1 and future Keymap analysis.
5. **Format drift**: MoErgo doesn't promise JSON stability [4]. Should the app validate strictly and refuse unknown shapes, or degrade gracefully?
6. **Macros and multi-character outputs**: should macros (and later mod-morphs) be taught as single "keys" that type strings?
7. **ZMK Studio on the user's Glove80**: does the user's firmware have Studio enabled, and can the Layout Editor turn it on (a `ZMK_STUDIO` config parameter on a v26.09+ build)? Only matters if a "read from keyboard" import is wanted after the MVP.
